## Historical diagnosis snapshot (superseded by later experiments)

The first proven blocker was depth initialization, not an inability to rasterize the title geometry. The unmodified title draw enables depth testing, disables depth writes, and uses LEqual. Its repaired 1920x1080 host depth image is created for the first time at the title draw and inherits guest `DB_DEPTH_CLEAR=0.0`, so every fragment was rejected. Generic first-use depth handling now selects the neutral value 1.0 for an uninitialized read-only LEqual test while retaining the guest clear value for later real initialization.

The generic first-use depth blocker is resolved. The title shader investigation also proved that translated SPIR-V, MRT routing, packed-half exports, stage linkage, and sampled color can all produce nonzero data. Controlled color injection isolated the remaining black-frame boundary to final pixel shader `0x500640200`. Forced color at composite PS `0x5006CD700` survives composite rasterization and upscaler CS `0x50068EF00`, producing a fully nonblack 2432x1368 input. Capturing the final PS's first image sample at PC `0x2C` also produces a fully nonblack flip buffer, proving its image ownership, descriptor binding, and coordinates are correct.

The newest generic fix corrects GFX10 `VCMPX` lowering: `VCMPX` writes EXEC only and must not overwrite the decoded SDWA scalar register pair. The shader saves EXEC in `s38:s39`, copies it to `s106:s107`, performs three conditional `VCMPX` regions, and restores EXEC from `s106:s107`; SharpEmu had destroyed that saved mask with each compare. With the correction, original shaders are no longer uniformly black, but only 4,823 dim pixels survive in a stable two-scanline strip at `y=0..1`. This is not the menu. Post-fix markers prove EXEC is active after the first sample and at pack convergence. The live scalar branch follows the long path through PC `0x63C`, not the previously suspected short path through PC `0x170`. Multi-point capture isolates the first magnitude collapse to `VMadF32 v4 <- v9,v4,v11` at PC `0x40C`: its input `v4` is one, its small addend `v11` is about 0.004, and multiplier `v9` from `ImageLoad` PC `0x31C` is zero. The bound 1x1 texture's first component is demonstrably float one. The descriptor is type 8 (1D), but SharpEmu accepted only type 9 (2D), so it replaced this real image with a zero fallback before upload. Allowing 1D images through the common height-1 Vulkan path now preserves the address and seeds the correct nonzero 16-byte texel. This produced the first visibly rendered 3D title geometry and a recognizable PlayStation Studios boot logo from original shaders. Both are dark blue with strong vertical striping, so the remaining rendering defect is color/texture/composite interpretation rather than missing geometry or rasterization. A separate generic `sce::Json` HLE now carries the room loader through its animation/material documents to `GAME: Level has started: title_controller_ship`; a clean sustained run must determine whether the intro continues to the ASTRO BOT title/menu before another shader probe is introduced.

A later title-loop draw was definitely lost: ES `0x5003EDF00` plus PS `0x5003EE900`, six vertices, failed translation every frame on VOP2 opcode `0x2D`. LLVM's GFX10 instruction definitions identify `0x2B`, `0x2C`, and `0x2D` as `V_FMAC_F32`, `V_FMAMK_F32`, and `V_FMAAK_F32`. SharpEmu was using the older `V_LDEXP_F32` meaning for `0x2B` and did not decode the two literal FMA forms. The decode fix now translates and executes this draw with no shader translation misses. It exposed a second generic bug: the resulting `R8G8B8A8Unorm` target was discarded when sampled through a legal `R8G8B8A8Srgb` mutable view. The compatibility fix now produces a cache hit, and address-filtered readback proves a forced color survives both writes to the 4K target. That auxiliary 4K path still does not feed the observed title presentation, so it is no longer the primary title/menu lead; return to the 1920x1080 title graph with both generic fixes retained.
